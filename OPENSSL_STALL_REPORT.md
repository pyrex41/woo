# PR11 OpenSSL chain verification diagnostic

This branch intentionally retains the original `t/alpn.lisp` OpenSSL verification calls from PR11 `a6352421`. It adds a ten minute GitHub Actions job timeout and a 540 second shell watchdog around the native test command. On a watchdog deadline, the step first records only the launched process group (at most 64 live PIDs), Linux `/proc/<pid>/wchan` values, and best effort GDB thread backtraces (at most 10 seconds per PID and 30 seconds overall). Collection uses a 4 MiB intermediate bound and emits a final 256 KiB report. It omits command arguments, environments, frame arguments, locals, cores, and heap dumps; termination happens after this pre-termination capture and preserves timeout status even if the child exits cleanly during TERM.

The repeated Linux stall is observed at `test-chain-trust-and-missing-intermediate`, but the low level cause remains UNKNOWN. The pinned ASDF/UIOP implementation documents nil input as the default null device and does not establish that stdin is inherited. A separate diagnostic run with explicit stderr capture completed both OpenSSL calls in about 9 to 10 ms; a follow-up without explicit nil input also passed. That verifies stderr capture as a reliable mitigation, but does not prove which lock, stream, or subprocess state caused the original stall.

The old failures and the successful reruns did not show a toolchain version change. The two failed attempts (`36520528290`, jobs `109252151245` and `109257916322`) and the diagnostic/fix runs (`36574486301`, `36575113239`, `36575639979`, and `36576400353`) all logged Roswell `26.02.116`, SBCL `2.6.9.roswell`, ASDF `3.3.1`, and the same Ubuntu image `20260920.314.1`. Every run downloaded the same SBCL archive, `https://github.com/roswell/sbcl_bin/releases/download/2.6.9/sbcl-2.6.9-x86-64-linux-binary.tar.bz2`. The installer itself is still moving: it is fetched from `https://raw.githubusercontent.com/roswell/roswell/master/scripts/install-for-ci.sh` and downloads the unpinned Roswell `https://github.com/roswell/roswell/archive/release.tar.gz`. Thus these receipts do not support toolchain drift as the explanation, but CI remains non-reproducible until Roswell and the resolved archive checksums are pinned and versions are emitted by the workflow.

The final mitigation under review captures OpenSSL stderr and asserts the complete chain exits 0 while the missing intermediate exits 2 with the expected issuer error. This diagnostic branch is for bounded evidence only and is not a production readiness claim.

The original-default variant was rerun under this watchdog at hosted run `36576400353` (job `109433018217`, commit `4ffebc4`). It completed successfully in about 203 seconds and all 20 tests passed, so no watchdog process-state dump was emitted. Since the original-default call also passed, the successful stderr-capture runs do not isolate stderr handling as the cause; they demonstrate a safe, stricter mitigation only. The non-reproduction confirms the low-level cause is nondeterministic/UNKNOWN.

A local blocked-child fixture with a TERM handler that exits 0 exercised the capture path and recorded the owned process group before sending TERM; it reported 210 bytes, captured a live owned PID, and still returned watchdog status 124. The macOS host lacked `setsid`, `timeout`, and `gdb`, so this used a Python process-group fallback and did not produce a native backtrace. The Linux workflow path uses those standard tools and remains diagnostic evidence only; it does not establish the OpenSSL cause.
